# Локальные действия, IME и подтверждения текста (R31)

Локальное действие меняет только интерфейс текущей страницы. Бизнес-команда всегда
проверяется сервером: право доступа, видимость/доступность виджета, схема события и
актуальность дерева не заменяются локальным результатом.

## API

```java
final InputField field = new InputField();
field.setInputDebounce(200); // 0 по умолчанию, диапазон 0..2000 мс
final Button button = new Button("Выделить текст");
button.onClickOnClient(new SelectText(field, 0, 5));
// Альтернативы: new Focus(field), new ScrollIntoView(field),
// new OpenPage("/catalog"), new OpenPageInNewTab("/help").
button.onClick(event -> {
    // Независимая серверная бизнес-команда, если она нужна.
});
```

Классы действий находятся в `com.kniazkov.widgets.client`. Обработчик задаётся заранее
и выполняется синхронно при click, в том числе при клавиатурной активации кнопки.
Это не команда «сначала запросить сервер, потом попробовать открыть окно».
Одна привязка содержит одно действие; повторная регистрация заменяет его.
`executeOnClient` для других типов событий не поддерживается локальным allowlist.
Для Enter в редакторе по-прежнему используются `onEnter`/`onKeyDown` и серверный обработчик.

| Действие | Контракт |
| --- | --- |
| `Focus(target)` | Фокус без прокрутки; только живой доступный target в том же runtime |
| `ScrollIntoView(target)` | Немедленная прокрутка к ближайшему краю, без анимации |
| `SelectText(target, start, end)` | Фокус и диапазон UTF-16 `[start,end)`; границы 0..65536, без вмешательства в активную композицию |
| `OpenPage(href)` | Навигация текущей вкладки, разрешены HTTP/HTTPS и относительные URL |
| `OpenPageInNewTab(href)` | `window.open` внутри исходного жеста с `noopener` |

Локальный диспетчер отделён от диспетчера серверных обновлений. В локальном payload
нельзя вызвать `reset`, `set text`, удаление дерева или произвольный JavaScript.
Проверяются имя команды, точный набор полей, типы, идентификатор target и диапазон.
`javascript:` и `data:` запрещены. Неизвестная/невалидная привязка не применяется;
при получении через последовательный протокол это ошибка обновления, а не тихое
подтверждение неподдержанной команды. Ранее доступные OpenPage/OpenPageInNewTab сохранены.

## Согласование с сервером

Committed-текст, накопленный debounce, ставится в очередь **до** click/keyboard/submit.
Локальный результат не ждёт RTT. Наличие локальной привязки само по себе не подписывает
сервер на click; для бизнес-команды нужен обычный `onClick`.

Сервер может отклонить действие. Это не откатывает уже выполненные focus/scroll/selection
и не закрывает открытую вкладку. Приложение должно показать отказ обычным серверным
обновлением. Нельзя считать открытие вкладки или фокус подтверждением покупки/входа.
При уходе на другую страницу обработчик старой страницы может не успеть выполниться:
для существенных операций сначала получают серверное подтверждение, а затем предлагают
отдельное явное действие пользователя.

## Ввод и IME

- InputField, PasswordInput, TextArea и наследники используют общий редактор.
- `compositionstart`/`compositionupdate` защищают промежуточный текст от отправки и
  серверной перезаписи. На `compositionend` отправляется только итог. Следующий
  одинаковый `input` не создаёт второе событие.
- Обычные события клавиш не превращаются в бизнес-команды без явной подписки.
  Enter, которым подтверждают композицию, не отправляет форму.
- Debounce — trailing edge, максимум одно накопленное значение на редактор.
  Значение 0 сохраняет немедленную отправку обычного ввода. Изменения текста с одинаковым
  содержимым не создают дополнительную команду.
- Blur отправляет накопленный committed-текст. Blur до compositionend не отправляет
  промежуточную строку; завершение композиции отправит итог даже после ухода фокуса.
- Окончательное удаление отменяет таймер. Временно отсоединённое дерево не отправляет
  текст; при возвращении сохранённый committed-ввод можно отправить. Активная
  композиция при отсоединении отменяется с восстановлением значения до её начала,
  поэтому незавершённый IME-текст не отправляется после возвращения.
- Пока пользователь редактирует поле, подтверждённая серверная нормализация откладывается
  до blur, не меняя value/selection. Новое локальное редактирование отменяет старую
  отложенную нормализацию. Ответ, который ещё не подтвердил последний text input,
  не может вернуть более старое значение после blur.
- Входящие значения во время несохранённого ввода/композиции игнорируются: приоритет у
  локального ввода. Это не механизм совместного редактирования. Если нужен принудительный
  сброс, приложение должно явно завершить/закрыть редактор, а не рассчитывать на перезапись
  активной композиции.

## Пример и проверка

Запускаемый пример: `com.kniazkov.widgets.example.LocalActions`; тестовый маршрут
`/local-actions`. Он показывает немедленный фокус одновременно с отказом серверной
команды, выделение, прокрутку, открытие вкладки и отложенную нормализацию в uppercase.
Это невизуальный контракт над существующими виджетами: новых классов Widget и изменений
их оформления нет, поэтому отдельный снимок в галерее не требуется.

Java-тесты проверяют сериализацию и ограничения API. JS-тесты проверяют композицию,
порядок событий, debounce, устаревшее подтверждение, каретку, уничтожение редактора,
локальные действия и запрещённый payload. E2E проверяет те же сценарии при задержанной
сети в Chromium и WebKit, а также реальное открытие новой вкладки и отсутствие opener.

Сценарий композиции в автоматическом браузере использует синтетическую последовательность
CompositionEvent/InputEvent с китайским текстом. Это проверка обработчиков библиотеки,
**не проверка настоящего системного IME**: в этом облачном прогоне системный IME
не настраивался и не проверялся. Нативный ввод китайского/японского текста, отмена выбора
и конкретная виртуальная клавиатура требуют отдельной ручной проверки.

Popup blocker остаётся решением браузера и настроек пользователя. Нельзя гарантировать
открытие из таймера, после await/ответа сервера либо из синтетического click. Даже при
реальном жесте расширения/политики браузера могут запретить окно. `noopener` может давать
`null` из window.open и при успешном открытии, поэтому библиотека не выдаёт ложного
подтверждения по возвращаемому WindowProxy.
