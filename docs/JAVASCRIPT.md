# Browser JavaScript source map

Browser code is organized by responsibility under `src/main/html/scripts`. These are classic
scripts, not ES modules. There is no bundler, new dependency or JavaScript build step.

## Scope and loading

`manifest.json` is the source of truth for the `shared`, `widgets` and `client` groups and their
loading order. `BrowserScripts` reads it from classpath resources. Unit-test helpers read the
same file instead of maintaining separate lists of sources.

1. `index.html` loads `options.js`, then the manifest's **shared** scripts as ordinary script tags.
2. `/scripts/page-runtime.js` is generated by the server. It places the **widgets** and **client**
   groups inside `createPageRuntime(page)` and returns its four lifecycle entry points.
3. `navigation.js` creates an independent runtime for each history entry, retains inactive pages,
   and restores their DOM and scroll position when navigating back.

The source files remain separate in the repository and JAR. The runtime still arrives in one
HTTP response, with source-path comments marking file boundaries. No `eval`, dynamic imports or
browser-global widget registry is introduced. Debug/release log handling and HTTP caching remain
on the same server paths.

**Do not add individual widget or client files as script tags.** Their shared lexical scope
belongs to one page. Widget IDs, upload queues, server checkpoints and event queues must stay
isolated between active and cached pages. Top-level state lives next to its owner: widget registry in `widgets/core.js`, uploads in
`widgets/uploads.js`, and client lifecycle, errors, protocol and synchronization in their
respective files. All of these declarations still belong to the same per-page lexical scope.

`navigation.js` and `options.js` remain intact: each already has a single responsibility and a
manageable size. Small related widgets share files; complex interactions have dedicated files.

## Adding or moving code

- Prefer an existing responsibility-focused file. Add a new file for a distinct subsystem, not
  for every function, and register it once in the appropriate manifest group.
- Function declarations can refer to functions in other files in the same runtime. Top-level
  initializers must respect manifest order; do not execute widget work before runtime creation.
- Register new widget types in `widgets/core.js` and new wire actions in `client/protocol.js`.
- Tests can load one manifest group with `readScriptGroup` or the complete factory with
  `readPageRuntime` from `src/test/js/helpers/scripts.js`.
- Run `mvn clean verify` after deleting or moving resources so stale scripts cannot remain in
  `target/classes` or the JAR. Then run `npm run test:browser`.

The manifest test catches omitted/duplicate source entries. HTTP tests check shared-script order
and generated runtime resources; navigation and browser tests exercise isolation and the full
Java-to-browser round trip.
