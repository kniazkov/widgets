# Dialog: подтверждение и асинхронная форма

`Dialog<T>` — одноразовый `ModalPopup` с существующими `Form`, `FormField`
и `Busy`. Он не создаёт второй механизм модальности. Пример находится
в `AllWidgets`, карточка «Диалоги с результатом».

## Результат и жизненный цикл

`result()` возвращает `CompletionStage<Dialog.Result<T>>`, завершающийся
ровно один раз. `reason()` различает `CONFIRMED`, `CANCELLED`, `CLOSED`.
`value()` возвращает `Optional<T>`: значение есть только при подтверждении.
Действие должно вернуть ненулевое значение; `null`, исключение или отмена
его future считаются ошибкой с возможностью повтора, а не подтверждением.
Изменение future, полученного через `result().toCompletableFuture()`,
не управляет диалогом.

| Действие | Результат | Во время busy |
| --- | --- | --- |
| Кнопка подтверждения, Enter, `confirm()` | Валидация → действие → `CONFIRMED` | Повторный запуск игнорируется |
| Кнопка отмены, `cancel()` | `CANCELLED` | Запрещено, метод возвращает `false` |
| Закрыть, `close()`, Escape, разрешённый outside-click | `CLOSED` | Запрещено |
| `dispose()`, закрытие страницы, принудительный `remove()` | `CLOSED` | Разрешено; ожидающее действие получает `cancel(true)` |

Escape включён по умолчанию, outside-click выключен. Настройки меняются
через `setCloseOnEscape` и `setCloseOnOutsideClick`. Busy временно выключает
оба пути и блокирует три встроенные кнопки. Сервер дополнительно проверяет
busy, поэтому устаревшее клиентское событие тоже не закроет диалог.
После ошибки исходная политика восстанавливается.

Успех, отмена и обычное закрытие вызывают `dispose()`. `remove()` сохраняет
обычный контракт отсоединения Widget, но завершает результат; такой экземпляр
нельзя использовать повторно. Для окончательного удаления используй `dispose()`.
Поздний результат после удаления, смены корня или закрытия страницы игнорируется.
Отмена future кооперативная: она не гарантирует остановки внешнего HTTP-запроса
или отката уже записанных данных. Идемпотентность бизнес-операций остаётся
ответственностью приложения.

## Подтверждение

```java
final Dialog.Messages messages = new Dialog.Messages(
    "Подтвердить", "Отменить", "Закрыть", "Сохраняем…",
    "Не удалось сохранить. Повторите попытку.", "Проверьте поля.");
final Dialog<Boolean> dialog = Dialog.confirmation(
    "Подтверждение", "Продолжить действие?", messages);
dialog.result().thenAccept(result -> {
    if (result.reason() == Dialog.Reason.CONFIRMED) {
        status.setText("Подтверждено");
    }
});
root.add(dialog);
```

`confirmation` возвращает `true` при подтверждении. Для операции, которую
нужно дождаться до закрытия окна, используй конструктор с асинхронным действием.

## Форма и повтор

```java
final Dialog<String> dialog = new Dialog<>("Учебная заявка", messages,
    values -> CompletableFuture.supplyAsync(
        () -> saveSample(values.get("sample")), applicationExecutor));
final FormField sample = new FormField("sample", "Название образца");
sample.setRequired(true);
dialog.addField(sample);
dialog.result().thenAccept(result -> result.value().ifPresent(status::setText));
root.add(dialog);
```

`applicationExecutor`, `saveSample` и `status` в примере принадлежат приложению.
Обработчик должен быстро вернуть `CompletionStage`; блокирующий ввод-вывод
нельзя выполнять на потоке страницы. Завершение переносится в `RootWidget.execute`.
Неасинхронные обработчики результата выполняются в контексте страницы; если
выбрано `thenAcceptAsync`, обновления UI нужно снова направить через `root.execute`.

`addField` использует серверную валидацию FormField, а `setValidator` принимает
`Function<Map<String,String>, Form.Result>` для общей проверки. Кнопка и Enter
используют один путь `Form.submit()`. Действию передаётся неизменяемый снимок
валидированных значений. Поля остаются редактируемыми во время ожидания;
это не меняет отправленный снимок. При повторе читаются актуальные значения.

Ошибка показывается через Busy с `messages.error()`, форма остаётся открытой,
данные сохраняются. Текст исключения пользователю не показывается. Для диагностики
приложение само журналирует ошибки своего действия. Все шесть сообщений обязательны
и непусты; библиотека не задаёт язык приложения. Дополнительное содержимое
помещается в `getContent()`, поля — через `addField`.

## Размеры, вложенность и доступность

По умолчанию ширина 560 px, но окно ограничено видимым viewport с отступами
12 px. Длинное содержимое прокручивается внутри окна. `visualViewport`
учитывается при появлении клавиатуры и сдвиге видимой области; без него
используется размер окна. Обработчики resize/scroll удаляются при detach/dispose.
Кнопки внутри Dialog имеют автоматическую высоту не менее 40 px и ограниченную
ширину: длинные локализованные подписи переносятся вместо обрезания. Это правило
имеет приоритет над фиксированной высотой кнопки. Пользовательские max-width/
max-height могут переопределить ограничения; после такого изменения проверь viewport.

Заголовок служит доступным именем. Стек, блокировка фоновой страницы, Tab/Shift+Tab,
Escape и возврат фокуса предоставлены ModalPopup. При перемещении фокуса внутри
Dialog соответствующий элемент прокручивается в видимую область. Вложенный
диалог добавляется как дочерний виджет родительского; закрывается верхнее окно,
фокус возвращается на его кнопку запуска, затем на исходную страницу.

Обычные ModalPopup/MessagePopup сохраняют прежнее поведение. Новый `dismiss()`
у ModalPopup по умолчанию вызывает `remove()`; Dialog переопределяет его для
busy-политики и результата. Изменение прокрутки фокуса ограничено Dialog.
