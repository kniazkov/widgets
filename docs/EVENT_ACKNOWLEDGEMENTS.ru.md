# Подтверждение событий и восстановление синхронизации (R03)

`lastEvent` — накопительное подтверждение **доставки**, а не успешного выполнения
бизнес-операции. Оно означает, что события до этого ID включительно больше нельзя
отправлять повторно. Протокол работает внутри авторизованного канала R01; проверка
возможностей виджета и данных описана в [R02](SERVER_EVENT_VALIDATION.ru.md).

## Терминальные результаты

Ответ синхронизации содержит `eventResults` для событий присланного пакета:

| `status` | Значение | `reason` |
| --- | --- | --- |
| `applied` | Событие прошло проверку и передано обработчику виджета | Не передаётся |
| `rejected` | Событие отклонено до вызова обработчика | `invalidEnvelope` или код проверки R02 |
| `obsolete` | Адресат уже удалён/не принадлежит этому дереву либо ID уже потреблён | `detachedWidget` / `alreadyConsumed` |

Каждый результат терминальный и продвигает `lastEvent`, если его ID новее предыдущего.
Повторный ID получает `obsolete / alreadyConsumed`: это не попытка восстановить результат
прежней бизнес-операции. Сервер хранит только верхнюю границу потреблённых ID, без растущего
журнала результатов. Дубликат с изменённым payload также не исполняется.

Для совместимости `rejectedEvents` из R02 сохранён: в нём остаются отказы и
`detachedWidget`. Новый код должен различать результаты через `eventResults`.

### Пример обмена

Пока ответ на удаление кнопки находится в сети, браузер успел поставить в очередь ещё
один её клик `#2` и клик другой, действующей кнопки `#3`. Ответ содержит:

```json
{
  "result": true,
  "lastEvent": "#3",
  "eventResults": [
    {"id": "#2", "status": "obsolete", "reason": "detachedWidget"},
    {"id": "#3", "status": "applied"}
  ],
  "rejectedEvents": [{"id": "#2", "reason": "detachedWidget"}]
}
```

Обычные `updates`, `serverId`, `clientAlive` и другие поля ответа в примере опущены.
Оба события удаляются из очереди; следующее допустимое действие отправляется нормально.
При потере этого ответа повтор `#2, #3` получит тот же `lastEvent`, а оба результата —
`obsolete / alreadyConsumed`; контроллер действующей кнопки второй раз не вызывается.

## Порядок и повреждённые пакеты

Перед вызовом первого контроллера сервер проверяет весь массив: элементы должны быть
объектами, ID — строками `#<положительное целое long>` в канонической записи, порядок —
неубывающим. Пропуски номеров разрешены, одинаковые ID дедуплицируются. Повреждённый JSON,
не-массив, отсутствующий/некорректный ID или убывающий порядок дают
`eventResyncRequired: true`. События такого пакета не выполняются, ACK не продвигается.
Пакет не сортируется: порядок действий задаёт отправитель.

При корректном ID неверный `widget` или нестроковый/отсутствующий `type` дают
`rejected / invalidEnvelope`. Неизвестное строковое имя события существующего виджета
даёт `rejected / unknownEvent`. Несуществующий или отсоединённый адресат даёт `obsolete`.

## Потеря ответа, исключения и бизнес-результат

ID потребляется под блокировкой корня **до** вызова прикладного обработчика. Это защищает
от повторения побочного эффекта, если контроллер сначала изменил данные, затем выбросил
исключение. Исключение продолжает идти через обычную диагностику; успешный ответ с
`applied` при исключении не отправляется. Повтор уже потреблённого ID не вызывает код снова.
`applied` не гарантирует валидность модели, наличие контроллера, завершение асинхронной
операции или фиксацию транзакции приложения.

Два настоящих клика имеют разные ID и оба обрабатываются; повторная доставка того же
ID — один вызов. Защита действует в пределах жизни одного серверного Client. Перезапуск
сервера, новый канал и повторное действие пользователя не образуют общей транзакции.
Для платежей и других внешних эффектов приложению по-прежнему нужны собственный ключ
идемпотентности и проверка бизнес-статуса. Пакет событий также не является транзакцией.

## Ограничение повторов и resync

Браузер отправляет снимок очереди и проверяет ответ относительно этого снимка. ACK не
может уменьшаться или подтверждать события, ещё не отправленные в этом запросе.
Числовая часть ACK должна помещаться в безопасное целое JavaScript (до 2⁵³−1).
`#?` означает исходный нулевой ACK; `#0` также принимается. Неизвестный/повреждённый ACK
или `eventResyncRequired` сразу запускает восстановление.

Если ответ пришёл, но из непустого отправленного пакета не подтверждено ни одного события:

1. После первого ответа повтор разрешается через 250 мс.
2. После второго — через 500 мс.
3. После третьего клиент прекращает отправку старой очереди и пересоздаёт страницу.

Таким образом, подряд возможны один запрос и два повтора без прогресса. Частичное
подтверждение сбрасывает счётчик; оставшаяся очередь продолжает отправляться. Один общий
таймер ограничивает все источники отправки: polling, новый ввод и callback загрузки файлов.
Потерянный/неразбираемый ответ повторяется с обычной задержкой polling 2500 мс; при этом
сохраняется действующая логика ошибки соединения. Это отдельный случай от полученного,
но не продвигающего ACK ответа; общая политика offline/reconnect относится к R08.

Восстановление закрывает старый канал отправки до вызова callbacks, отменяет таймер
повтора и использует существующее пересоздание Page с теми же URL, query и TabContext.
Ожидающие callbacks получают `false`; поздние ответы старого runtime игнорируются.
Очередь не переносится в новый Client: неизвестно, какие действия сервер уже успел
выполнить. Поэтому неподтверждённый ввод и несохранённое локальное состояние могут быть
утрачены; приложение должно показывать фактический сохранённый результат после resync.
Автоматического повтора бизнес-действий под новыми ID нет.

## Совместимость и проверка

Новый сервер сохраняет `lastEvent` и `rejectedEvents`, поэтому существующий браузер
освобождает очередь после терминального отказа. Новый браузер не требует `eventResults`
для удаления очереди и может ограничить повторение старого сервера с неподвижным ACK.
Сторонние отправители должны соблюдать монотонность и каноническую запись ID; новые
проверки намеренно отвергают повреждённые последовательности.

Поиск по текущему дереву между событиями описан в [R04](LIVE_EVENT_TARGETS.ru.md). Квоты размера
очереди/пакета — R17. Здесь не меняются транспорт, публичный Java API и виджеты.
AllWidgets и снимки галереи обновления не требуют: изменение невизуальное.

Интеграционный маршрут `/event-ack` существует только в E2E-сервере. Тесты перехватывают
реальные запросы/ответы: удерживают ответ после удаления, теряют ACK после вызова
контроллера и подменяют ACK на неподвижный. Во всех случаях проверяются последующие
допустимые действия. Результаты сборки: [R03_VERIFICATION.ru.md](R03_VERIFICATION.ru.md).
