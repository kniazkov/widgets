# Инкрементальная синхронизация и адаптивный polling

R32, issue #136. Изменение невизуального контракта: новые виджеты и снимки AllWidgets не требуются.

## Сервер

`RootWidget` хранит слабый индекс изменённых смонтированных виджетов. `pushUpdate` добавляет виджет в индекс; коллекция забирает снимок индекса и опустошает только соответствующие очереди. Порядок протокола по-прежнему задаёт `Update`/`TreeSet`, а не порядок индекса. Пустая коллекция не обходит дочерние контейнеры.

При attach в индекс попадают уже накопленные изменения всего присоединяемого поддерева. При detach виджет исключается из индекса прежнего корня, но сохраняет свою ограниченную очередь до повторного attach. Move, reactive model callbacks, очистка страницы и переполнение сохраняют прежние правила. Превышение бюджета требует resync, а не молчаливой потери изменений. Слабые ссылки не удерживают забытые отсоединённые виджеты.

Блокировка индекса не захватывает блокировки виджетов. Перед вызовом внешней коллекции очередь снимается с виджета и его монитор освобождается: фоновое изменение модели может безопасно создать следующую очередь.

Собственные виджеты должны публиковать изменения через `pushUpdate`; создание изменений ленивым переопределением `getUpdates` не поддерживается инкрементальным сборщиком. Структурные операции приложения по-прежнему следует выполнять через `root.execute(...)`. Изменение модели не требует полного обхода страницы.

## Браузер

Один координатор и один deadline-таймер обслуживают все runtime одного документа. Отдельные вкладки независимы. Объединяется планирование страниц, **не HTTP-конверты**: токены, event ACK и update checkpoint остаются отдельными для каждой страницы. Мультиплексирование транспорта — отдельная R34.

- Активная страница: после полезного ответа или события — 2500 мс; после пустых ответов — 5000, затем максимум 10000 мс.
- Кешированная страница или скрытый документ: максимум 30000 мс. Возможен один уже назначенный короткий опрос после скрытия.
- Сервер возвращает `pollingMaxDelay = min(30000, clientLifetime / 3)` (минимум 1 мс); это верхний предел всех интервалов. Старый сервер без поля сохраняет 2500 мс.
- Возврат видимости немедленно опрашивает активную страницу. Back/Forward проверяет серверный экземпляр и применяет накопленные обновления **до показа** сохранённого DOM.
- События, продолжение пакетов обновлений, upload callbacks и восстановление сети не ждут polling. Существующий retry/backpressure gate остаётся единственным входом в транспорт.
- Кеш не замораживается: сохраняются лимиты очередей, размер кеша, TTL и полная пересборка после expiry/resync. При disposal запись координатора удаляется; после последней страницы удаляются таймер и listener.

Компромисс: произвольное серверное изменение на спокойной активной странице может появиться через 10 секунд, в фоне — через 30 секунд плюс RTT. Браузер вправе сильнее ограничивать фоновые таймеры или замораживать вкладку; после истечения серверного lifetime выполняется штатная пересборка. Это не гарантия heartbeat в замороженном браузере.

## Интеграционный пример

```java
final StringModel value = new StringModel("initial");
final TextWidget label = new TextWidget(TextWidget.getDefaultStyle(), value);
root.add(new Section(label));
// После получения результата фоновой операции:
root.execute(() -> value.setData("completed"));
```

Изменение только `label` попадает в dirty-index. Browser fixture `/polling` и `/polling-next` показывает одну общую модель в двух кешируемых страницах: действие на второй странице изменяет также отсоединённую первую; Back сохраняет её DOM. В браузерном тесте отдельно проверяется пересоздание после TTL.

## Проверки и измерения

`DirtyUpdatesTest`: add/remove/move, повторное подключение, модель в отсоединённом поддереве, перенос ещё не экспортированного дерева, dispose, отсутствие обхода 1000 неизменных виджетов. Существующий `ClientProtocolTest.backgroundModelUpdateIsSafeWhileClientCollectsUpdates` проверяет конкурентную запись во время передачи очереди.

`polling.test.js`: единый таймер, backoff, ограничение lifetime, скрытие/возврат видимости, удаление последнего runtime. `navigation.test.js` сохраняет проверки истории, метаданных, отложенных ответов и отзыва контекста. `polling.spec.js` проверяет реальный Java→HTTP→DOM путь в Chromium/WebKit, фоновые изменения, Back и TTL; visibility-событие управляется синтетически, системное замораживание вкладки этим не проверяется.

Воспроизводимый микростенд:

```sh
mvn -Dtest=PollingBenchmarkTest -Dwidgets.pollingBenchmark=true test
npm run test:js
mvn verify
npm run test:browser
```

Сравнение с `bb23a40` (тот же `PollingBenchmarkTest` скопирован в отдельный checkout) выполнено на облачном Linux 6.18.57, AMD EPYC 9V74, OpenJDK 21.0.13, Maven 3.9.9. По 50 текстовых виджетов на клиента, 10 прогревочных и 30 измеряемых пустых синхронизаций. Измеряется CPU текущего потока и сериализованный JSON ответа; HTTP, TLS, браузер и ожидание polling в этот микростенд **не входят**. Это последовательные вызовы независимых клиентов, не тест 1000 конкурентных соединений.

Расчёт установившегося режима (не замер HTTP): одна активная страница — 0.4 → 0.1 запроса/с; активная плюс три кешированные — 1.6 → 0.2 запроса/с.
