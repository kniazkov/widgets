# Защита клиентского канала

Начиная с R01 / [#105](https://github.com/kniazkov/widgets/issues/105), одного `clientId`
недостаточно ни для чтения обновлений страницы, ни для выполнения её событий.
Изменение несовместимо со старыми самописными HTTP-клиентами протокола. Java-приложение
и встроенные скрипты нужно обновлять вместе.

## Что проверяет сервер

| Значение | Назначение | Где находится |
| --- | --- | --- |
| Cookie с 256-битным секретом | Принадлежность браузерной транспортной сессии | HttpOnly, host-only cookie; на сервере — `BrowserSession` |
| `X-Widgets-Session` | Несекретный UUID поколения bootstrap, для восстановления других вкладок после смены cookie | HTML и заголовок запроса; сам по себе не даёт доступа |
| `X-Widgets-CSRF` | Подтверждение доступа к HTML своего origin | Отдельный 256-битный секрет в bootstrap HTML и памяти документа |
| `X-Widgets-Channel` | Доступ к конкретной странице | Отдельный 256-битный секрет из ответа `new instance`, в памяти runtime страницы |
| `X-Widgets-Epoch` | Актуальная эпоха сервера | `serverId` из ответа `new instance` |
| `clientId`, `browserId`, `tabId` | Адресация и метаданные | Не являются доказательством авторизации |

Секреты генерируются `SecureRandom`. Они не передаются в URL, параметрах страницы,
`localStorage` или `sessionStorage`. Штатная диагностика не записывает заголовки и cookie;
из сообщения браузера дополнительно удаляются секреты его сессии и канала.

Проверка cookie, CSRF и Origin общая для всех действий. Перед обращением к существующему
клиенту сервер под его блокировкой проверяет владельца, секрет канала, эпоху и отзыв.
Это относится к `synchronize`, `upload chunk`, `kill`, `report error`. Чужой запрос
не подтверждает ACK, не забирает очередь обновлений, не продлевает жизнь клиента,
не выполняет контроллер и не расходует разрешённую диагностическую запись.

`RootWidget.downloadFile(...)` не создаёт отдельный публичный URL: содержимое файла
передаётся в обновлении `download file` через защищённую синхронизацию. Приложение
по-прежнему обязано проверить право пользователя на файл **до** вызова этого метода.
Публичные static sources не превращаются в защищённое хранилище.

## HTTP и reverse proxy

Все действия протокола выполняются только через `POST /`. Вызов `GET /?action=...`
возвращает `405` с `Allow: POST`. Ответы протокола, отказы и HTML bootstrap имеют
`Cache-Control: no-store`. Авторизованные запросы без существующего клиента сохраняют
обычный ответ `clientAlive: false`, чтобы браузер мог восстановить страницу.

Если присутствует `Origin`, он должен совпадать с origin приложения; `null`, чужой
origin и неоднозначные заголовки отклоняются. Если присутствует `Sec-Fetch-Site`,
разрешён только `same-origin`. Отсутствие этих браузерных заголовков допускается
для HTTP-клиентов, но **не отменяет** проверку cookie, CSRF и секрета канала.
CORS для сторонних origin не включён. Несколько значений защитного заголовка или
несколько одноимённых сессионных cookie отклоняются.

Для прямого запуска origin определяется по SSL-настройке сервера и заголовку `Host`.
За reverse proxy, особенно при завершении TLS на proxy, необходимо указать внешний адрес:

```java
final Options options = new Options.Builder()
    .setPort(8080)
    .setPublicOrigin("https://shop.example")
    .build();
Server.start(application, options);
```

`setPublicOrigin` принимает HTTP(S) origin без логина, пути, query и fragment;
конечный `/` и стандартный порт нормализуются. Proxy должен передавать `Origin`,
`Cookie`, `X-Widgets-*`, `Sec-Fetch-Site`, не кешировать bootstrap/протокол и не публиковать
закрытый listener. `Forwarded` и `X-Forwarded-*` автоматически не считаются доверенными.

На HTTPS используется `__Host-widgets-session; Secure; HttpOnly; SameSite=Strict; Path=/`,
без `Domain`. На прямом HTTP для разработки — `widgets-session` с теми же ограничениями,
кроме `Secure`. HTTP не защищает секреты от перехвата в сети: производственный сайт
должен использовать HTTPS. При навигации с другого сайта `SameSite=Strict` может не
передать прежнюю cookie; сервер создаст новую транспортную сессию. Не используйте её
как самостоятельный механизм постоянного входа пользователя.

## Жизненный цикл, вкладки и история

1. HTML bootstrap переиспользует живую серверную сессию из cookie или создаёт новую.
   Новый секрет никогда не принимается из запроса клиента.
2. `new instance` требует cookie и CSRF, создаёт канал с собственным секретом и возвращает
   `id`, `channelToken`, `serverId`, `tabId`.
3. Каждое следующее действие передаёт cookie автоматически, а остальные доказательства —
   только в заголовках. Кешированные страницы одного документа сохраняют свои секреты
   в runtime, поэтому Back/Forward не требуют открытия чужого канала.
4. Документы одного браузера делят транспортную сессию, но получают отдельные `TabContext`.
   Навигация внутри документа переиспользует его `TabContext`; скопированный `tabId` другого
   владельца не принимается даже при совпадающем, подставленном `browserId`.
5. Успешные создание/синхронизация/загрузка продлевают живую сессию. Её предельное время
   простоя задаётся `Options.Builder.setClientLifetime(...)`, по умолчанию три минуты.
   Чужие запросы, диагностика и `kill` не поддерживают сессию искусственно.
6. После обычного кратковременного обрыва сети используются прежние доказательства.
   После истечения срока, отзыва или перезапуска сервера они не восстанавливаются:
   сервер отвечает `403 {"sessionExpired":true}`, браузер перезагружает весь документ,
   получает новую cookie/CSRF и создаёт новые каналы. Несовпадение поколения
   `X-Widgets-Session` со сменившейся общей cookie также перезагружает старую вкладку. История не оживляет старые деревья.
7. Несовпадение владельца, CSRF, секрета или эпохи даёт `403 {"accessDenied":true}`.
   Клиент показывает `Client Error` и прекращает повторы этого runtime; это не временная
   сетевая ошибка. Удалённый собственный клиент пересоздаётся с новым секретом.

## Связь с авторизацией приложения

`PageContext.browserSession` — проверенная транспортная сессия, **не пользователь**.
`getId()` возвращает её несекретный серверный UUID. `browserId` остаётся входными
метаданными для совместимости: его можно подставить, поэтому нельзя по нему одному
выбирать авторизованного пользователя, его корзину или привилегии.

При входе, выходе, смене пользователя или отзыве прав приложение должно обновить своё
состояние авторизации и вызвать `context.browserSession.revoke()`. Отзыв окончателен и
затрагивает все каналы этой сессии, включая другие вкладки и историю. Новый bootstrap
получит новый `getId()`; перенос разрешённой бизнес-сессии на него — ответственность
приложения с собственной проверкой учётных данных.

Минимальный пример события завершения транспортной сессии (также проверяется E2E):

```java
final Page page = (root, context) -> {
    final Button endSession = new Button("Завершить сеанс");
    endSession.onClick(event -> {
        // Здесь приложение сначала завершает собственную сессию авторизации.
        context.browserSession.revoke();
    });
    root.add(new Section(endSession));
};
```

Состояние сессии проверяется повторно после ожидания блокировки корня, перед каждым
событием пакета и после контроллеров перед сбором обновлений, в том числе после upload.
Если контроллер отзывает сессию, оставшиеся события пакета и его приватные обновления
не выполняются/не выдаются. Уже исполняющуюся бизнес-операцию или ответ, уже отправленный
в сеть, отзыв отменить не может. Проверку бизнес-прав и изменение бизнес-состояния нужно
сериализовать в самом приложении; транспорт не заменяет эту транзакцию.

У созданного вручную `PageContext` поле может быть `null`. Внутрипроцессные тесты могут
создавать такие несвязанные клиенты; HTTP всегда создаёт связанные и никогда не
принимает отсутствие владельца как обход защиты.

## Проверки

- `ClientChannelSecurityTest`: настоящий HTTP, два независимых владельца, подмена ID,
  отсутствие/подмена секретов, эпоха, все действия, приватные данные и download, GET/CSRF,
  Origin, повтор события, kill, истечение срока, отзыв всех вкладок, смена транспортной
  личности, отзыв посередине пакета и запрос, уже ожидающий блокировку корня при logout.
- Там же: отсутствие утечки секретов через диагностику, cookie-флаги, HTTPS proxy origin,
  отказ доверять подставленным `X-Forwarded-*`.
- JS: POST и заголовки всех действий, обработка `403`, отсутствие бесконечных повторов.
- `channel-security.spec.js`: два настоящих браузерных контекста, чужие sync/kill/report,
  сохранение работоспособности владельца, отзыв нескольких вкладок, Back/Forward,
  отсутствие секретов в Web Storage и недоступность cookie из JavaScript.
- Существующие тесты проверяют собственные загрузки, скачивания, reconnect и историю.
  Новые E2E выполняются в Chromium и WebKit.

Видимых виджетов R01 не добавляет: галерея и AllWidgets сохраняют существующее покрытие.
