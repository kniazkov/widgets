# Обработка файлов и изображений

Загрузка бинарных частей и обработка готового файла имеют разные бюджеты.
Ограничения `UploadLimits` по-прежнему относятся к файлам и временным
байтам с момента выбора до завершения обработки. Готовые файлы обрабатывает
пул приложения: по умолчанию 4 задачи одновременно, очередь не длиннее
`min(filesPerApplication, 1024)`. Для другого режима настройте
`Options.Builder.setUploadProcessing(workers, queued)` (1–32 потока,
1–1024 ожидающих обработчика). Выбирайте параллелизм с учётом памяти,
которую потребляют декодеры и собственный обработчик приложения.

Если очередь заполнена к моменту получения последнего чанка, сервер
отклоняет загрузку с `uploadError: "processingBusy"`, удаляет её временные
данные, не ставит callback и не выдаёт успешный receipt. Браузер объясняет
отказ и предлагает выбрать файл позже; автоматической повторной обработки
нет. Уже принятые файлы продолжают обрабатываться. При закрытии страницы
или приложения ожидающие и выполняемые задачи отменяются, временные файлы
освобождаются. Пользовательский код должен учитывать прерывание; отмена
не откатывает выполненные им внешние действия.

`onLoad` выполняется в фоновом пуле. Выполняйте чтение, декодирование и
другую затратную работу в этом callback и не передавайте временный
`UploadedFile` за его границы. Готовый результат публикуйте через
`descriptor.executeOnRoot(Runnable)`: короткая операция синхронизируется
с событиями браузера и обновлениями прогресса. Она возвращает `false`,
если файл отменён, загрузчик перенесён вне страницы или страница закрыта.
`root.execute(Runnable)` подходит для других фоновых задач, привязанных
к той же странице. Не запускайте чтение, ожидание или декодирование внутри
этого блока. Общая модель, которую используют разные страницы, остаётся
ответственностью приложения и должна иметь собственную синхронизацию.

```java
loader.onSelect(descriptor -> descriptor.onLoad(file -> {
    try {
        final var limits = ImageDecodeLimits.defaults();
        if (file.getSize() > limits.maxEncodedBytes()) {
            throw new IOException("Encoded image exceeds size limit");
        }
        final var decoded = ImageLoader.load(file.getType(), file.getContent(), limits);
        descriptor.executeOnRoot(() -> status.setText("Width: " + decoded.getWidth()));
    } catch (final IOException invalid) {
        descriptor.executeOnRoot(() -> status.setText("Image could not be decoded"));
    }
}));
```

`ImageLoader` до выделения декодированных пикселей проверяет размер
закодированного файла, ширину и высоту, число пикселей и оцениваемую память
для растра, конвертации и поворота. По умолчанию: 32 МиБ входных данных,
8192 пикселя на сторону, 16 млн пикселей, 256 МиБ оцениваемой рабочей памяти
(16 байт на пиксель). Для HEIC учитываются также размеры исходных кадров.
Это консервативная оценка, не гарантия объёма JVM для стороннего декодера.
Свой бюджет передайте через `ImageDecodeLimits`. Перегрузка `load(File)`
читает ограниченный объём, а при работе с upload проверьте размер до
`getContent()`. Превышение или ошибка формата возвращают `IOException`;
следующие файлы можно обрабатывать. Новый виджет не добавляется.

Для локальной проверки в тестовом `E2ETestServer` откройте
`/bounded-image-processing`: обычный PNG 16×16 отклоняется низким лимитом
теста, обычный PNG 8×8 даёт «Decoded 8 x 8» после прогресса 100%. Страница
`/bounded-processing-queue` в `UploadBoundaryServer` позволяет вручную
заполнить очередь, увидеть объяснение и освободить первый обработчик.
