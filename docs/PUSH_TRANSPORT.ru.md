# Push-транспорт и каналы страниц (R36)

HTTP остаётся транспортом по умолчанию. Для включения WSS приложение явно запускает
`PushServer` после HTTP-сервера. Один документ браузера открывает один сокет;
активная и кешированные страницы имеют отдельные подписки, токены, updateEpoch,
номера событий и подтверждения обновлений. Разные вкладки открывают разные сокеты.

```java
final Application app = new Application((root, context) -> {
    root.add(new TextWidget("Hello"));
});
Server.start(app, new Options.Builder()
    .setPort(8080)
    .setBindAddress(InetAddress.getLoopbackAddress())
    .setPublicOrigin("https://example.com")
    .build());
final PushServer push = PushServer.start(app,
    StreamOptions.defaults(8081, "https://example.com"));
// push.close(): выключить WSS, оставить HTTP работающим.
// app.close(): остановить оба listener и фоновые задачи.
```

Импорты: `com.kniazkov.widgets.base.*`, `com.kniazkov.widgets.view.TextWidget`,
`java.net.InetAddress`. Полный проверяемый пример с двумя страницами, фоновым
изменением, upload и отзывом сессии:
[`PushTestServer`](../src/test/java/com/kniazkov/widgets/e2e/PushTestServer.java).
Нового видимого виджета нет: AllWidgets и галерея не меняются.

## Развёртывание и совместимость

`PushServer` использует настоящий Jetty WebSocket из R35, а не WS→HTTP bridge.
Не запускайте отдельно `StreamServer` на том же порту: push уже владеет адаптером.
Listener доступен только на loopback. Настройки TLS, Origin, cookie, Upgrade и
пример Nginx приведены в [STREAM_SERVER.ru.md](STREAM_SERVER.ru.md).
HTTP и WSS обязаны иметь один public origin. Proxy направляет `/widgets-stream`
на порт 8081, остальные пути — на 8080. Включите HTTP/1.1 upgrade, отключите
buffering; пример read/send timeout — 75 секунд при стандартных heartbeat/deadline.
Не подменяйте Origin и не публикуйте внутренние порты.

Сервер рекламирует `pushPath` и `pushMessageBytes` в ответе создания страницы
только при работающем `PushServer`. Старый клиент игнорирует эти поля и продолжает
HTTP; новый клиент без них также работает по HTTP. Если WebSocket недоступен,
upgrade заблокирован или AUTH не завершился, интерфейс продолжает HTTP-обмен.
Создание/удаление страниц, диагностика и бинарные upload всегда используют HTTP.

## Протокол

После cookie/Origin-проверки upgrade клиент отправляет AUTH R35 с bootstrap
session/CSRF; секреты остаются в памяти, не в URL и не в localStorage. После ready:

| Сообщение | Назначение |
|---|---|
| `subscribe {client,channel:{token,epoch,updateEpoch}}` | Проверка владельца и создание логической подписки; ответ `subscribed {client}` |
| `unsubscribe {client}` | Удаление подписки, не удаление самой страницы; принятые команды могут завершиться |
| `dirty {client}` (сервер → браузер) | Подсказка получить накопленные изменения конкретной страницы |
| `ackHint {client}` | Разрешить следующую подсказку; **не** подтверждать обновления |
| `request {id,query,channel}` | `query` содержит прежний synchronize: client, events, lastUpdate; channel содержит token, epoch, updateEpoch |
| `response {id,data}` | Прежний JSON synchronize с lastEvent, updates, resync и независимой эпохой страницы |
| `http {id}` | Ответ слишком велик для WS: повторить исходный запрос через HTTP |
| `lease` / ответ `lease` | Продлить срок жизни подписанных страниц/вкладок и проверить доступность канала |

`id` — возрастающий положительный безопасный JS integer внутри физического
соединения. Это идентификатор запроса, не бизнес-события. Только synchronize
разрешён через WS; он вызывает тот же серверный обработчик, что HTTP. Владелец,
токен страницы и серверная эпоха проверяются перед обработкой каждого запроса.
Ошибки приложения возвращают прежний `clientError`, без текста исключения.

Push устроен как invalidation → synchronize → delta: сервер раз в 100 мс сравнивает
атомарные ревизии корней, не сериализуя чистые деревья. На страницу хранится не
более одной неподтверждённой подсказки. Получив её, клиент сразу запрашивает delta
по WSS. Изменение во время текущего запроса вызывает дополнительную синхронизацию.
Это сохраняет единый ACK/replay-контракт ценой дополнительного обхода сети для
самостоятельного серверного изменения. В отсутствие изменений нет пустого
synchronize polling; остаются короткие lease и native ping/pong.

Кешированная страница остаётся подписанной и обновляется в фоне. Back/Forward
обязательно выполняет synchronize перед показом сохранённого DOM даже при живом WSS.
Её уничтожение
снимает подписку. Уничтожение последней страницы закрывает сокет. Native heartbeat
проверяет транспорт; документная lease (не реже раза в 5 секунд) дополнительно
продлевает прежние клиентские idle budgets, как раньше это делал polling. Она
**не** двигает checkpoint. После потери соединения действуют обычные сроки жизни
сессии/страниц; logout/revoke закрывает сокет и требует нового bootstrap.

## Восстановление и ограничения

При обрыве незавершённые запросы завершаются локальной сетевой ошибкой ровно один
раз. Повтор сохраняет исходные event ID и lastUpdate; серверная дедупликация
защищает от повторного действия при потере ответа. Новое соединение подписывает
те же страницы; поздние кадры старого сокета отбрасываются. Если replay уже
невозможен, работает существующий snapshot/resync с новой updateEpoch.
После рестарта процесса старая server epoch отклоняется и клиент создаёт новые
страницы. Одновременная ротация общей cookie несколькими вкладками допускает до
трёх попыток обновления документа с jitter; ошибки кешированных страниц объединяются
в одну попытку. Успешное создание страницы сбрасывает этот бюджет. Бесконечная
перезагрузка при запрещённых cookies/недоступном storage не допускается.
Это **не** долговременная дедупликация между процессами и не репликация
бизнес-данных: модель нескольких серверов остаётся задачей R37.

AUTH/ready ограничен 8 секундами на клиенте, запрос — 10 секундами. Отсутствие
lease ACK закрывает канал через max(10 секунд, три интервала lease). Переподключение
использует существующую экспоненциальную задержку с jitter и пределом 15 секунд;
HTTP доступен во время ожидания. Избыточный размер запроса сразу переводит его
на HTTP; избыточный ответ вызывает `http {id}` и replay того же запроса. Нельзя
терять большие snapshot или преждевременно подтверждать их ради лимита WS.

Бюджеты `StreamOptions` продолжают действовать: по умолчанию 1024 соединения,
64 KiB на кадр, 64 сообщения/256 KiB исходящей очереди на соединение. Дополнительно:

- Не более 64 подписок и 64 незавершённых запросов на документ.
- Отдельный общий пул протокола: `workers` потоков и `tasks` мест очереди
  (по умолчанию 4/64), помимо такого же пула парсинга native адаптера.
- Каждый запрос ограничен `timeoutMillis` с учётом ожидания в очереди. Перегрузка
  или deadline закрывает соединение; клиент использует HTTP.
- Ревизии проверяет один daemon timer. Он не берёт монитор client/root и не вызывает
  бизнес-код. Сетевые записи выполняются вне блокировок приложения/виджетов.
- Закрытие соединения отменяет ожидающие задачи, прерывает работающие и освобождает
  подписки. Java не может остановить handler, игнорирующий interrupt: используйте
  конечные таймауты внешних операций. Медленный канал не блокирует другой канал,
  пока в ограниченном общем пуле есть свободный worker.

## Наблюдаемость, rollout и откат

`push.getMetrics()` возвращает gauges R35 (`connections`, `activeHandlers`,
`queuedHandlers`, `outgoingMessages`, `outgoingBytes`) плюс `subscriptions`,
`pushWorkers`, `pushTasks`. В них нет токенов/ID/пользовательских сообщений.
Следите за заполнением очередей, непрерывными переподключениями, HTTP fallback,
ошибками upgrade и клиентскими ошибками, а также heap и задержкой click→DOM.
Количество сокетов должно соответствовать числу документов, а не виджетов.
Не включайте дампы AUTH/заголовков/бизнес-кадров в публичные логи.

Включайте сначала на тестовом инстансе, затем на ограниченной группе экземпляров
с закреплением сессии за одним сервером. Сравните фоновые обновления, ошибки,
задержку и память с HTTP при одинаковой нагрузке. Не включайте push ради обещания
автоматического ускорения клика: эту выгоду измеряют отдельно.

Для отката вызовите `push.close()` или уберите запуск `PushServer` из конфигурации.
HTTP продолжит обслуживать страницы и upload; новые страницы больше не получают
рекламу push. Уже открытые документы перейдут на HTTP, но могут пытаться восстановить
WSS с ограниченным backoff до перезагрузки. Перезагрузка процесса не нужна для
отключения listener. Повторный close безопасен.

## Проверки

```sh
mvn -B -ntp verify
npm ci
npx playwright install --with-deps chromium webkit
npm run test:browser
mvn -B -ntp -DskipTests test-compile dependency:build-classpath \
  -Dmdep.outputFile=target/runtime-classpath.txt
node scripts/run-push-probe.mjs
```

`PushServerTest` повторяет контракт replay/ACK через HTTP и push, проверяет
независимость каналов, потерю ответа, чужого владельца, oversized snapshot,
медленный handler, исключение после побочного эффекта и откат на HTTP.
`push-transport.test.js` проверяет один сокет, маршрутизацию ответов, generation
fence, timeout, lease, HTTP fallback и освобождение запросов.

Workflow `Push transport` запускает настоящий Chromium через TLS reverse proxy
на native Java WebSocket. Одинаковая нагрузка для HTTP и push: 8 документов,
20 последовательных кликов в каждом, 12 секунд простоя. Артефакт `push-probe`
содержит SHA, версию браузера, p50/p95 click→DOM, количество POST/WS synchronize/
control кадров и heap до/после. Это интеграционный сравнительный образец, не
статистически контролируемый heap benchmark и не предельная производительность.

Дополнительные сценарии: cached pages, Back/Forward без пересоздания, фоновое
изменение, потерянный ACK без повторного действия, отказ proxy, reconnect,
задержка WS-кадров, HTTP upload 64 KiB, рестарт Java, logout и возврат gauges к нулю.
Прежние полные Java/JS/browser проверки сохранены. Самоподписанный сертификат
используется только тестовым proxy, его приватный ключ не публикуется.
