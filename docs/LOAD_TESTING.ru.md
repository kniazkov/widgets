# Нагрузочный стенд и метрики (R33)

Стенд проверяет HTTP-протокол Widgets и бизнес-результаты при росте числа каналов.
Он запускает отдельный Java-процесс на loopback, создаёт синтетические страницы,
завершает их и проверяет освобождение ресурсов. `--browser` дополнительно запускает
настоящий Chromium. В production ничего автоматически не включается.

## Воспроизведение

Нужны Java 21, Maven, Node.js 22+ и зависимости из `package-lock.json`:

```sh
npm ci
mvn -B -ntp verify dependency:build-classpath -Dmdep.outputFile=target/runtime-classpath.txt
npx playwright install --with-deps chromium
node scripts/run-load.mjs --browser --clients=1,100,1000 --repeats=2 --dom-samples=100
```

Для короткой проверки без браузера:

```sh
node scripts/run-load.mjs --clients=1,4 --repeats=1 --profiles=burst,uploads,history
```

Параметры: `--clients` (1…1000), `--profiles`, `--repeats` (1…10),
`--concurrency` (1…64, по умолчанию 16), `--dom-samples` (1…1000), `--output`.
Создание и завершение каналов ограничено числом HTTP workers; нет мгновенного
неограниченного запуска тысячи запросов. При ошибке новые работы прекращаются,
уже начавшиеся дожидаются завершения, каналы закрываются и Java останавливается.
HTTP timeout — 15 секунд, проверка освобождения ресурсов — до 10 секунд.

Workflow [Load profiles](../.github/workflows/load-tests.yml) запускает полную матрицу
при изменении стенда и вручную через workflow_dispatch. Лимит job — 25 минут.
Обычный workflow Tests остаётся без сокращений: `mvn verify` на Linux/Windows и
`npm run test:browser` (включая JavaScript-тесты и браузерные сценарии).

## Профили и проверки

| Профиль | Нагрузка и критерий корректности |
|---|---|
| `polling` | 1/100/1000 одновременно живых каналов; десять пустых round trips, каждый возвращает пустой список обновлений. С браузером далее непрерывный фоновый polling и 100 последовательных кликов наблюдателя. |
| `burst` | По четыре пачки из восьми команд на канал; повтор каждой пачки с теми же ID не меняет счётчик. Пачка из 65 событий отклоняется лимитом 64; пересоздание канала сохраняет бизнес-состояние и позволяет выполнить новую команду. |
| `large-tree` | По 256 строк (Section + TextWidget), команды и их повторы. Всего 1/100/1000 клиентов, волнами до 16 живых деревьев. |
| `slow-client` | Клиент не подтверждает полученное изменение; после 1800 мс превышен специально уменьшенный до 1500 мс срок replay-очереди. Сервер требует resync, новая страница того же документа получает ровно один выполненный инкремент. |
| `uploads` | 1/100/1000 файлов по 64 КиБ с одинаковыми известными байтами, волнами до 16 страниц. Единственный обработчик и одно место очереди; при `processingBusy` создаётся новый descriptor. Проверяются байты, успешное завершение, повтор финального чанка и единственный callback. |
| `history` | 1/100/1000 документов, до 16 одновременно; в каждом четыре страницы с общей моделью (до 64 серверных страниц). Изменение одной видно в трёх остальных. |

Большие деревья, uploads и история намеренно имеют ограничение одновременно живой
нагрузки. 1000 здесь означает **общее число обработанных клиентов/документов**, а не
1000 одновременно тяжёлых деревьев. `logicalClients`, `peakLiveLimit` и
`serverPageLimit` в отчёте отличают эти величины. У burst и у браузерного
наблюдателя может быть дополнительная страница; при параллельном resync — до
`min(clients, concurrency)` временных страниц. Стенд проверяет верхние границы
живых страниц и числа upload workers/элементов очереди по выборкам. `peak` — наблюдавшийся максимум,
снятый раз в 200 мс, а не точный максимум между выборками.

Отдельный browser history probe проверяет реальный Back/Forward, сохранение DOM,
обновление общей модели в фоне и пересоздание DOM после TTL кеша. Время браузера
для TTL ускорено Playwright clock; время сервера не подменяется. Это отдельная
проверка корректности, её время не включается в latency бюджет.

После каждого профиля новая выборка обязана показать ноль страниц, виджетов,
обновлений, ожидающих/активных операций и загрузок (включая очередь обработки).
Ненулевой результат, потерянная/повторная команда, испорченный файл или таймаут
завершают прогон ошибкой. Сам тестовый словарь бизнес-состояния сохраняется до
завершения процесса, чтобы проверять resync; это не production-хранилище.

## Что измеряется

`target/load-results/report.json` содержит SHA и признак изменённого рабочего дерева,
CPU/число доступных процессоров/RAM/ОС, версии Java/Node/Chromium, параметры нагрузки,
результаты каждого повторения и бюджеты. На виртуальной машине это видимые гостю
ресурсы, а не гарантированная выделенная производительность. `metrics.jsonl` —
исходный числовой журнал; `server.log` — ошибки тестового сервера. CI сохраняет
все три файла в artifact `load-results` на 7 дней, включая неудачные запуски.

- `httpMs`: p50/p95/p99/max времени протокольного POST, включая чтение ответа.
  `requests/requestBytes/responseBytes` считают POST нагрузочного клиента, тело
  multipart и UTF-8 JSON соответственно. HTTP/TLS-заголовки, bootstrap GET,
  статика и отдельный трафик браузерного наблюдателя сюда **не входят**.
- `eventToDomMs`: только профиль polling с `--browser`; от вызова Playwright click
  до появления точного следующего значения счётчика в настоящем DOM. Включает
  ожидание клика и накладные расходы автоматизации; это end-to-end наблюдение,
  не чистая задержка сети. Без браузера samples=0 и percentiles=null, не ноль мс.
- CPU — разность process CPU time JVM; heap — выборочный максимум; GC — разности
  количества/длительности сборок. CPU Node и Chromium не включён.
- Lock wait — накопленное время ожидания мониторов канала и root, включая
  накладные расходы измерения. Это не profiler всех блокировок JVM.
- В фазу включены создание, работа, остановка и ожидание контрольной выборки.
  JVM одна на весь прогон; отдельного прогрева каждой фазы нет. Первые и повторные
  запуски отличаются JIT/GC, поэтому сравнивать следует одинаковый порядок профилей.

Квантили — nearest rank: элемент `ceil(p*n)` отсортированной выборки. На малой
выборке p99 близок к максимуму и не является надёжной оценкой хвоста распределения.

## API метрик и интеграция

`Application.getMetrics()` возвращает неизменяемый `Map<String, Long>` с фиксированными
ключами. Он не создаёт HTTP endpoint, не выдаёт адреса, ID страниц, токены, значения
полей или имена файлов. Приложение само определяет доступ к внутреннему мониторингу.
Пример запуска сборщика вне обработчиков UI:

```java
var executor = java.util.concurrent.Executors.newSingleThreadScheduledExecutor();
application.onClose(executor::shutdownNow);
executor.scheduleWithFixedDelay(() -> {
    var snapshot = application.getMetrics();
    System.out.println(snapshot); // либо ваш закрытый числовой exporter
}, 0, 5, java.util.concurrent.TimeUnit.SECONDS);
```

| Ключи | Семантика |
|---|---|
| `pages`, `widgets` | Число серверных каналов и принадлежащих им незавершённых виджетов, включая root. Это не число DOM-узлов. |
| `dirtyWidgets`, `bufferedUpdates`, `bufferedUpdateBytes` | Грязные виджеты и ещё не опубликованные обновления/оценка их размера. |
| `pendingUpdates`, `pendingUpdateBytes` | Опубликованная replay-очередь, ожидающая ACK. |
| `rootWaiters`, `activeOperations`, `completedOperations` | Ожидающие root, работающие под root и завершённые synchronize/upload операции. Счётчик включает отклонённые операции, прошедшие до этого уровня. |
| `rootLockWaitNanos`, `rootLockMaxWaitNanos` | Сумма и максимум времени ожидания root с начала жизни приложения. |
| `channelWaiters`, `channelActiveOperations`, `channelCompletedOperations` | Аналогичные агрегаты на входе в таблицу клиентов и монитор канала. Попытка к уже отсутствующему каналу также завершается и учитывается. |
| `channelLockWaitNanos`, `channelLockMaxWaitNanos` | Сумма и максимум ожидания входа в канал; включает ожидание ConcurrentHashMap.computeIfPresent. |
| `uploads`, `uploadReservedBytes`, `uploadProcessing`, `uploadQueued` | Активные upload descriptors, зарезервированные байты, активные фоновые обработчики и очередь executor. |
| `heapUsedBytes`, `gcCount`, `gcMillis`, `processCpuNanos` | Вся JVM, а не отдельный Application; processCpuNanos=-1, если JVM не поддерживает счётчик. |

Счётчики времени/завершений накопительные; gauge значения текущие. Снимок
**не атомарен между страницами**. Явная выборка обходит страницы/виджеты и берёт
мониторы root: она может ждать пользовательский обработчик и сама влияет на
измерения. Не вызывайте её из UI handler или при удержании root другой страницы:
это создаёт риск взаимной блокировки. Обычный synchronize не обходит все страницы
ради метрик; на горячем пути добавлены только числовые счётчики времени/операций.

`RootWidget.getDiagnostics()` предоставляет локальный снимок виджетов и raw-очереди;
`UploadRegistry.getProcessingCount()/getQueuedCount()` — состояния executor.
Изменение добавочное, wire-протокол и существующие Options не меняются. Новых
видимых виджетов нет, поэтому AllWidgets и изображения для этого контракта не нужны.

## Базовая линия и бюджеты

[Предварительный прогон](LOAD_BASELINE.ru.md) фиксирует два запуска без браузера.
Окончательные браузерные результаты текущего PR берутся из его CI artifact и
указываются в описании PR вместе с SHA; локальный прогон не подменяет эту приёмку.

Для одинаковых profile/clients отчёт вычисляет для CPU, HTTP p95 и DOM p95
`investigationThreshold = max + (max - min)` по повторениям. Это порог расследования,
основанный на измеренном разбросе, **не SLA и не автоматический запрет merge**.
Два повторения недостаточны для статистической гарантии. При превышении сравните
CPU/RAM/версии/порядок/JIT, повторите прогон и только затем принимайте решение.
Результаты разных машин и браузерные/небраузерные прогоны напрямую несопоставимы.

Строгие CI-бюджеты относятся к корректности и ограниченности ресурсов: лимит
пачки, срока replay, bounded upload worker/queue, отсутствие потерянных/повторных
команд, нулевые живые ресурсы после остановки. Значения производительности не
выдаются за доказательство работы произвольного приложения под 1000 пользователями.
