# Проверка событий на сервере (R02)

Проверка канала R01 удостоверяет отправителя, но не делает его события доверенными.
Сервер проверяет каждый event до изменения модели и вызова контроллера под блокировкой
корневого виджета. Проверяется текущий корень, затем hidden/disabled самого виджета и
всех предков, возможность принимать событие и payload. Учитываются серверные свойства
`State.ANY / HIDDEN / DISABLED`, включая назначенные через общий `getModel`.
CSS (например, прозрачность или перекрытие другим элементом) не является проверкой прав.

## Допустимые события

| Событие | Возможность виджета | Данные |
| --- | --- | --- |
| `text input` | `HasTextInput`, а не `HasText` | Только строка `text`, максимум 65 536 UTF-16 code units по умолчанию |
| `check` | `HasCheckedState` | Только boolean `state`; RadioButton принимает только `true` |
| `select` | `HasSelectedIndex` | Только целое `index`, разрешённое `acceptsSelectedIndex` |
| `reorder` | `SortableSection` | Целое неотрицательное `revision`, строки `child`/`before` до 64 символов; прежняя проверка ревизии и членов контейнера остаётся обязательной |
| `dismiss` | `ModalPopup` с `closeOnOutsideClick=true` | Пустой объект |
| `focus`, `blur` | `HandlesFocusEvents` | Пустой объект |
| `click`, `pointer enter/leave/down/up` | `HandlesPointerEvents` | Полный PointerEvent, см. ниже |
| `upload` | `FileLoader` | Метаданные загрузки с проверкой типов, размера и числа чанков |

DropDownList принимает `-1` (нет выбора) и индексы существующих опций; Carousel —
только индексы существующих изображений. Custom-виджет с `HasSelectedIndex` должен
переопределить `acceptsSelectedIndex`; по умолчанию браузерный выбор запрещён.

PointerEvent требует `position` с четырьмя точками (`element`, `client`, `page`, `screen`),
каждая с целыми `x/y` в диапазоне int32; `keys` с boolean `ctrl/alt/shift/meta`;
boolean `primary`; целое `buttons` от 0 до 63; конечное число `pressure` от 0 до 1;
`type`: `mouse`, `touch`, `pen` либо пустая строка для активации без устройства.
Клиент нормализует отсутствующие у MouseEvent поля: type="", primary=true, pressure=0.
Это сохраняет клики с клавиатуры и браузеры, где click ещё является MouseEvent.

UPLOAD требует положительные целые `fileId` и `totalChunks`, целое неотрицательное
`size` не выше Options.maxFileSize; имя 1..255 символов без слешей и NUL, MIME-строку
до 255 символов. Число чанков должно соответствовать размеру и Options.chunkSize
(для пустого файла — один). ACCEPTED_FILES остаётся подсказкой выбора, а не проверкой
содержимого файла. Ресурсные квоты и очистка загрузок относятся к R05/R16/R17.

Все перечисленные payload допускают только перечисленные поля; нет приведения
строк к числам/boolean, усечения дробных индексов или игнорирования лишних полей.
Неизвестные события не вызывают контроллер. Ограничения очереди и размера всего
пакета относятся к R17; данный контракт ограничивает значения отдельных событий.

## Ответ и границы атомарности

Корректный sync с отклонённым событием получает HTTP 200 и обычные обновления плюс:

```json
{"rejectedEvents":[{"id":"#42","reason":"unsupportedEvent"}],"lastEvent":"#42"}
```

Коды: `unknownEvent`, `inactiveWidget`, `unsupportedEvent`, `invalidPayload`,
`detachedWidget`. Ответ не отражает payload. ID отклонённого адресованного события
подтверждается, поэтому браузер удаляет его из очереди и не повторяет бесконечно.
Существующий клиент использует `lastEvent`; отдельного окна протокольной ошибки нет.
Серверная модель остаётся прежней, локально подделанный DOM не является её состоянием.
`Event.rejectionReason` позволяет получить тот же код при прямой Java-интеграции;
`Event.process`/`Widget.handleEvent` также отбрасывают недопустимые события.

Атомарность относится к отказу **одного события**: до проверки не изменяются модель
и прикладной счётчик, контроллер не вызывается. Пакет не является транзакцией:
ранее принятые события сохраняют свои эффекты. Прикладные исключения не скрываются
под видом протокольного отказа. Несуществующие адресаты и повреждённые конверты без
пригодных ID — отдельный контракт R03. Поиск новых узлов, созданных внутри того же
пакета, остаётся задачей R04; R02 повторно проверяет принадлежность уже найденного узла.

Бизнес-валидация (например, незавершённый email в EmailModel) работает как раньше:
строка допустима по протоколу, модель получает её и сообщает `isValid=false`,
контроллер может показать прикладную подсказку. Это не `invalidPayload`.
Проверка прав на покупку, удаление и другие бизнес-действия остаётся у приложения.

## Интеграция и совместимость

```java
final InputField input = new InputField() {
    @Override
    public int getMaxInputLength() {
        return 200_000;
    }
};
input.onTextInput(value -> saveDraft(value));
```

Больший лимит стоит задавать только для предназначенных для длинного текста полей.
Программные `setText`/`setSelectedIndex` не являются браузерными событиями и сохраняют
собственные контракты. Custom-ввод должен реализовать HasTextInput; прикрепление
контроллера TEXT_INPUT к TextWidget больше не разрешает его редактирование.
Нестандартные Event не входят в сетевой реестр; расширение сетевого протокола требует
явной поддержки и проверки, одного `setController` недостаточно. Для собственного
Event, вызываемого только из Java, можно переопределить `rejectionReason` с явной
проверкой его контракта; это не регистрирует новый сетевой тип.

Новых видимых виджетов нет, внешний вид не меняется. AllWidgets и изображения галереи
обновления не требуют. Интеграционный пример выше и тестовый маршрут `/event-validation`
демонстрируют контракт; последний существует только в E2E-сервере.
