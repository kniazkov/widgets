# Владение UI, несколько узлов и восстановление (R37)

**Решение:** один Java-процесс владеет конкретной браузерной сессией и всеми её
страницами. Поддерживаются один узел и несколько независимых узлов со строгой
привязкой сессии к владельцу. Перенос живого дерева, прозрачный failover запросов
и active-active обработка одного UI не поддерживаются.

Существующие проверки владельца/токена/эпохи уже реализуют эту границу. R37
фиксирует deployment-контракт и проверяет его двумя независимыми JVM за TLS
балансировщиком. Новый кластерный API или скрытая репликация не добавляются.

## Что где хранится

| Состояние | Владелец и время жизни | После потери процесса |
|---|---|---|
| BrowserSession, cookie credential, CSRF, отзыв | Память одного Application | Новая транспортная сессия; прежняя cookie не авторизует запрос |
| Client, TabContext, дерево, модели UI, контроллеры и подписки | Память владельца страницы | Создаются заново фабрикой Page |
| serverId | Случайная эпоха Application | Новый UUID даже при том же порте/имени узла |
| channelToken, updateEpoch, event/update ACK, replay queue | Один канал в одной эпохе | Старые данные не переносятся на новый канал |
| Незавершённый ввод и upload | Браузер/эфемерные ресурсы владельца | Автоматическое сохранение не обещается |
| Заказы, остатки, бизнес-черновики, права пользователя | Авторитетное хранилище приложения | Повторно читаются новым владельцем после авторизации |
| Идемпотентность бизнес-команды | Уникальный ключ + результат в транзакции доменного хранилища | Сохраняется независимо от UI event ID |

JDBC-реализация Storage не делает BrowserSession, Java closure и обработчики
распределёнными. Сохранённая модель не равна воспроизводимому дереву UI. Фабрика
страницы должна уметь восстановить представление по бизнес-идентификаторам из URL
и durable данным, повторно проверив права. Секреты, channelToken и серверные
контроллеры не сериализуются в браузерное хранилище или общий Redis «как есть».

## Маршрутизация

Пример развертывания на одном публичном origin `https://example.com`:

| Маршрут | Узел A | Узел B |
|---|---|---|
| HTTP, bootstrap, synchronize, upload, cleanup | 127.0.0.1:8080 | 127.0.0.1:8090 |
| `/widgets-stream` (WSS upstream) | 127.0.0.1:8081 | 127.0.0.1:8091 |

Оба узла запускают обычный `Server.start` и опциональный `PushServer.start` с
одинаковым publicOrigin, но отдельными локальными портами, как в
[PUSH_TRANSPORT.ru.md](PUSH_TRANSPORT.ru.md). Listener готов принимать трафик
только после запуска **обоих** транспортов. Балансировщик завершает TLS и
сохраняет Origin, Cookie и WebSocket subprotocol/Upgrade.

Балансировщик выбирает владельца при первом bootstrap и выдаёт собственную
Secure/HttpOnly affinity cookie с Path=/ (в стенде `__Host-widgets-node`).
Все вкладки одной браузерной сессии, HTTP-запросы, upload и WSS используют одного
владельца. Привязка только WebSocket, только страницы, либо только IP недостаточна.
Affinity cookie — подсказка маршрутизации, **не авторизация**. Её подмена не должна
позволять использовать чужие widget credentials: сервер всё равно проверяет
BrowserSession, CSRF, channelToken и serverId. Рекомендуется подписывать routing
cookie на балансировщике, но это не заменяет проверок приложения.

Для уже закреплённой сессии:

- Нет retry/hedging protocol POST на другом backend, даже при timeout/502/503.
  Для Nginx требуется отключить `proxy_next_upstream` на этих маршрутах; обычная
  upstream-балансировка сама по себе не обеспечивает этот контракт.
- Нет автоматической смены владельца при отказе WSS: HTTP fallback идёт тому же
  владельцу. Отказ только WSS не означает потерю состояния Java-приложения.
- Отсутствующий/не готовый владелец → 503. Неверно доставленные credentials → 403
  (`sessionExpired` или `accessDenied`), без исполнения событий и изменения ACK.
- HTTP и WSS должны использовать одну таблицу маршрутизации и одну readiness-модель.
  Не публикуйте backend-порты наружу в обход этих правил.

Round-robin одного UI, transparent failover POST, смешивание HTTP/WS владельцев
и «общая cookie с разными локальными сессиями» **неподдерживаемы**. Библиотека не
может проверить конфигурацию внешнего балансировщика заранее: она явно отклоняет
чужие credentials, а не исполняет запрос на случайно совпавшем clientId. Бесконечные
попытки bootstrap ограничены клиентским бюджетом восстановления R36.

## Потеря владельца, рестарт и перенос

1. Прекратить направлять новые запросы к потерянному владельцу; возвращать 503.
2. Подтвердить fencing старого процесса: остановить/изолировать его от ingress и
   бизнес-записей. Сетевой timeout сам по себе не доказывает, что процесс умер.
3. Явно сменить routing assignment на готовый новый узел. Это административная
   операция, а не повтор уже отправленного бизнес-запроса.
4. Старые session/channel/epoch отклоняются. Браузер выполняет новый bootstrap;
   после рестарта меняется serverId даже на прежнем узле. Новая Page заново
   проверяет бизнес-авторизацию и загружает durable данные.
5. Старые UI-события с неопределённым результатом не подаются в новое дерево.
   Проверить результат операции через доменное хранилище. Повтор бизнес-команды
   допускается только с прежним durable idempotency key и серверной проверкой прав.

Уже исполняющийся handler нельзя отменить задним числом. Fencing, транзакционные
блокировки/ограничения и таймауты внешних вызовов — обязанности приложения и
инфраструктуры. Exactly-once между JVM не следует из локального event ACK.
Тестовый счётчик представляет эффект одной уникальной строкой. Для настоящего
заказа регистрация operation key, изменение заказа и сохранение результата должны
выполняться **одной** транзакцией. Для внешней оплаты нужен также контракт
идемпотентности провайдера либо outbox/сверка; UI event ID для этого недостаточен.

Rolling update: прекратить выдачу новых affinity к старому узлу, дать существующим
сессиям завершиться в ограниченный срок, затем выполнить fencing и явный перенос.
Миграции бизнес-схемы должны быть совместимы с одновременно работающими версиями.
Откат версии процесса не восстанавливает прежние UI-эпохи и Java-контроллеры.

## Авторизация и logout

BrowserSession подтверждает транспортное владение, а не вход пользователя.
Локальный `browserSession.revoke()` отзывает все каналы этой сессии у её владельца,
включая WSS. При строгой affinity другие вкладки той же сессии попадают туда же.
После failover тестовая страница требует новый вход; durable счётчик сам по себе
не восстанавливает полномочия.

Logout на одном узле **не** является глобальным logout пользователя на всех
устройствах/узлах. Если приложению нужен такой контракт, оно хранит авторитетную
версию авторизации/отзыв в общем хранилище и проверяет её при бизнес-операциях.
Доступ к записи и изменение записи должны быть согласованы транзакционно, иначе
между проверкой и эффектом возможна гонка. Недоступное хранилище прав не разрешает
исполнять защищённую операцию. При изменении прав локальные BrowserSession следует
отзывать; при переносе старый владелец должен быть fenced.

## External sessions и event bus

| Вариант | Что даёт | Чего не даёт / условия |
|---|---|---|
| Общая бизнес-БД + локальный UI (выбранный базовый вариант) | Восстановление по durable данным, доменная идемпотентность | Не переносит login/UI; требует affinity и нового bootstrap |
| External auth/session store | Общий principal, сроки и версия отзыва | Нужен отдельный адаптер приложения, проверки прав/недоступности; не хранить произвольные контроллеры |
| Event bus для invalidation | Сообщить владельцам, что доменные данные изменились | Возможны задержки, повторы и потеря сообщений; перечитывать источник истины, хранить версии/offset при необходимости |
| Репликация дерева/Java closures | Не выбрана | Не определены сериализация, ownership, side effects и совместимость версий; не поддерживается библиотекой |

Bus не подтверждает widget update ACK и не исполняет событие браузера повторно.
При внешней модификации БД обычный StringModel сам не обновится: приложение должно
перечитать данные и опубликовать изменение владельцу через безопасный lifecycle
(`executeOnRoot` для короткого обновления UI). Медленная работа с БД выполняется
вне root monitor. Формат события bus — доменный ID/версия, не channelToken и не UI
JSON. Shared auth и bus оцениваются здесь как расширения приложения, не как уже
реализованные возможности Widgets.

## Проверяемый стенд

[`DeploymentTestServer`](../src/test/java/com/kniazkov/widgets/e2e/DeploymentTestServer.java)
запускается **дважды**, в отдельных JVM с независимыми BrowserSession/serverId.
Node TLS proxy маршрутизирует настоящий HTTP и native WSS. SQLite используется
только как локальная durable бизнес-БД двух процессов на одной машине; это не
рекомендация размещать SQLite на NFS или использовать её как кластерную БД.
`Demo login` — намеренно тестовая имитация проверки прав, не готовый login API.

```sh
mvn -B -ntp verify
npm ci
npx playwright install --with-deps chromium webkit
npm run test:browser
mvn -B -ntp -DskipTests test-compile dependency:build-classpath \
  -Dmdep.outputFile=target/runtime-classpath.txt
node scripts/run-deployment-probe.mjs
```

`DeploymentModelTest`: чужая cookie и чужая эпоха не запускают обработчик; повтор
на владельце не дублирует событие; revoke запрещает старый канал; конкурентный
business key сохраняется один раз и читается после повторного открытия БД.

Workflow `Deployment model`: неверная маршрутизация HTTP и WSS, независимые
владельцы, принудительное завершение owner, 503 без автоматического повторения на
другом узле, явный перенос, новый вход, восстановление счётчика, durable повтор
операции, рестарт, logout и освобождение соединений. Артефакт `deployment-probe`
содержит SHA, browser version, результаты, журналы и числовые gauges; не содержит
cookie/CSRF/channelToken, SQLite-файл или приватный TLS-ключ. Диагностический HTML
при ошибке относится только к публичной тестовой странице.

Это невизуальная задача: новые пользовательские виджеты не добавляются, отдельные
снимки/изменения AllWidgets не требуются. Readiness/fencing и sticky routing стенда
проверяют контракт, а не конкретный production ingress-продукт.
